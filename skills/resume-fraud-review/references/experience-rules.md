# 公司特定经验规则

招聘团队可在此补充观察到的模式、反例和面试验证问题。

每条规则建议使用以下格式：

## 规则：`<简短名称>`

- **适用背景**：适用的岗位、级别、技术栈或公司类型。
- **观察到的模式**：包装简历中经常出现的现象。
- **为什么重要**：背后的技术或流程原因。
- **启发式强度**：弱 / 中 / 强。
- **反例**：看起来相似但合理的情况。
- **验证问题**：一个或多个具体问题或材料。
- **不可推断内容**：这条规则不能证明什么。

优先记录有多次招聘证据支持的规则。既要记录确认的疑点，也要记录误报和合理反例，让 Skill 随使用逐步提高准确性。
## 规则：已确认的公司经历包装

- **适用背景**：招聘方已通过工商、社保、背调、前雇主或其他可靠渠道确认公司不存在、候选人未任职，或任职信息与记录不符。
- **观察到的模式**：简历将该公司经历写成完整的测试岗位，通常同时包含项目职责、缺陷数量、修复率、性能测试和工具使用。
- **为什么重要**：这不是简历文案本身的推测，而是外部核验确认的事实；同一经历中的附属成果和指标需要重新核验。
- **启发式强度**：强，但只针对已核实的公司/任职事实及其关联主张。
- **反例**：公司更名、主体变更、外包派遣、项目制合作、实习证明主体与业务品牌不同；这些情况必须先核清主体关系。
- **验证问题**：核对劳动/实习主体、任职时间、汇报对象、项目交付物、代码或缺陷系统记录；逐项确认该段经历中的个人贡献。
- **不可推断内容**：不能仅因一段公司经历被确认包装，就自动断言教育经历、个人项目或其他任职经历全部虚假。
## 规则：公司业务与技术岗位匹配度

- **适用背景**：核验简历中的软件测试、QA、开发或产品岗位所属公司。
- **观察到的模式**：公司公开主营业务与互联网/软件技术完全无关，且搜索不到开发、测试、产品等技术岗位招聘信息；或者公司业务、产品和招聘记录能够互相对应。
- **为什么重要**：真实的软件测试岗位通常会在公司业务、产品、技术团队或招聘痕迹中留下至少一部分可交叉验证的信息。
- **启发式强度**：业务完全不相关且无内部 IT/外包解释时为中到强；仅缺少招聘信息时为弱。
- **反例**：制造、零售、教育、医疗等传统行业也可能有内部 IT 团队；招聘信息可能已下线，或岗位由外包公司发布。
- **验证问题**：核对公司实际产品/系统、研发团队归属、技术岗位招聘时间、外包或派遣主体、办公地点和直属主管。
- **不可推断内容**：没有公开技术招聘信息，不能单独证明公司虚假或候选人未任职。
